# ASIA EDITION — інструкція розгортання

2026-10-22. Зовнішні кроки тільки після окремого дозволу. Поточний стан: [LAUNCH_READINESS.md](LAUNCH_READINESS.md).

Для ручного застосування через Supabase SQL Editor використовуйте [SUPABASE_SQL_EDITOR.md](SUPABASE_SQL_EDITOR.md): додатковий preflight, точні залежності, контрольні SELECT після кожного файла та правила зупинки при помилці. Інструкцію перевірено локально; віддалені міграції агентом не виконано.

## Порядок розгортання після окремого дозволу

1. Зберегти незмінний source/lockfile; перевірити Node >=20.9, рекомендовано сумісний Node 24. `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`. Локальний повторний build у старому `.next` мав Turbopack/PostCSS cache panic; clean output `NEXT_DIST_DIR=qa/launch-build` успішний. Не видаляти активний користувацький кеш; CI збирати з чистого checkout/output. Однаковий NEXT_DIST_DIR для build/start.
2. За повідомленням власника, в існуючому staging вже застосовані 001–005 і `supabase/catalog-worker-role.sql`. **Не повторювати їх і не створювати інший проєкт.** Статус застосування оновленої 006 ще потрібно підтвердити; продовжувати тільки з першого незастосованого файла після окремого дозволу. Повний порядок лише для нової порожньої БД: 001 → 002 → 003 → 004 → `supabase/catalog-worker-role.sql` → 005 → 006 → 007. Наявна 007 потребує окремого погодження, новий файл 007 не потрібен. Embedded bootstrap з auth stubs на Supabase **не запускати**. Вести ledger; перед змінами інвентаризувати БД і зробити backup.
3. Review/apply `supabase/catalog-server-roles.sql`: три NOLOGIN/noinherit/nobypassrls role wrappers. DBA окремо вмикає LOGIN і призначає різні паролі у vault. Не використовувати postgres/service_role як app DB login. Жодної membership anon/authenticated. Перевірити SET ROLE та реальні відмови RLS для кожного login.
4. Review/apply `supabase/storage-private.sql`: новий `asia-private-media`, без public/browser policies. Файл навмисно rollback, якщо є будь-які наявні object policies або bucket уже public; DBA перевіряє їх на широку OR-доступність, не вимикає захист і не публікує bucket. Legacy `storage-admin.sql` для нового private контуру не застосовувати. Дані локальних фото самі не переміщуються — потрібен погоджений copy/manifest/SHA-процес до зміни backend.
5. У server secret manager заповнити [config/production.env.example](../config/production.env.example), не `.env.local`. Значення режиму: `ADMIN_MODE=supabase`, `TOUR_DATA_SOURCE=postgres`, `POSTGRES_RUNTIME=native`; лише після дозволу `POSTGRES_REMOTE_ENABLED=true`, approved host, три DB URL, CA за потреби, Supabase Auth URL/public key. Private Storage вмикається окремо через `PRIVATE_STORAGE_ENABLED=true`, server Storage URL/key/bucket. Server Storage key ніколи не NEXT_PUBLIC. SITE_URL — кореневий HTTPS origin.
6. Staging захистити паролем/мережею; `SITE_INDEXING_ENABLED=false`, `INQUIRIES_ENABLED=false`. Запустити `pnpm start` і окремий `node --import tsx scripts/catalog-worker.ts` під supervisor з restart/backoff та grace >=60 с. Worker використовує тільки реальні дозволені feeds, не синтетику. Budget: max pool × replicas × Next/worker reader/editor/worker pools, узгодити з лімітом DB/pooler. Session/transaction pooler та SET LOCAL ROLE/транзакції перевірити фактично, не припускати сумісність.
7. Перевірити health, login, import/resume/restart, photos/private access, rights, stale-version refusal та явну публікацію **окремої staging fixture**. Порядок роботи з фото: завантажити → зберегти галерею → у редакторі в блоці «Права на фотографии» вказати статус і HTTPS-підтвердження для кожного керованого фото → зберегти перевірку. Нові фото мають unknown і не доступні публічно. Зміна прав знімає пов'язані картки з публікації; повторне підтвердження не публікує їх. Далі перевірити права на продукт і окремо дозволити публікацію. Перевірити RU/EN, mobile/desktop, фільтри та відсутність provider/rights evidence у public payload. Лише тоді ввімкнути `INQUIRIES_ENABLED=true` + випадковий `INQUIRY_SIGNING_KEY` >=32 символи і перевірити запис/дедуп/спам/admin inbox. Це не бронювання.
8. Налаштувати proxy: HTTPS/HSTS, body limit ≥9 MiB для upload (і окремий малий ліміт inquiries), request timeouts, rate limits, no shared cache для `/admin`, `/api`, private media та динамічного каталогу. Запустити моніторинг HTTP5xx/latency, health, worker journal/lease failures і вільного Storage. Не логувати DSN, токени, email чи тексти заявок. Не розгортати worker як безконтрольний фон усередині serverless request.
9. До production cutover налаштувати шифровані DB backups/PITR та private media backup. Для узгодженого snapshot тимчасово зупинити нові записи/worker, зробити `pg_dump --format=custom --no-owner --no-acl` під окремим backup-account та copy private objects + SHA manifest; відновити в іншу БД/bucket і порівняти кількості/контрольні суми. Строки й частоту затверджує власник. Дії тут **не виконувалися**.
10. Після staging sign-off — окреме погодження production міграцій/deploy/DNS. Зберегти попередній release і backups, rollback через повернення release/flags, а не DROP SQL. Публікувати лише індивідуально затверджені продукти. Увімкнути індексацію `SITE_INDEXING_ENABLED=true` лише після перевірки copy/канонічного домену/robots/sitemap. Для >10 000 публічних продуктів розбити sitemap (нинішній bounded sitemap до 10 000 продуктів).
