# Адміністрування ASIA EDITION — фаза 4

Адреса: `/admin`. Інтерфейс російською; публічні сторінки залишаються RU/EN, з російською за замовчуванням і рівно 13 країнами. Без конфігурації панель закрита і показує інструкцію налаштування. Спільного пароля за замовчуванням немає.

## Локальна розробка без Supabase

1. У каталозі проєкту запустіть `pnpm admin:setup` в інтерактивному терміналі. Вкажіть email і пароль із щонайменше 12 символів. Пароль вводиться приховано; зберігається лише scrypt-хеш. Повторний запуск не перезаписує обліковий запис.
2. У `.env.local` встановіть `ADMIN_MODE=local`, `TOUR_DATA_SOURCE=local`, `NEXT_PUBLIC_SITE_URL=http://localhost:3000`. Наявні ключі не потрібно змінювати. `ADMIN_LOCAL_DIRECTORY` не задавайте: адміністрація й каталог використовуватимуть `.admin-local/tours.json`.
3. Перезапустіть сервер: `pnpm dev --hostname 127.0.0.1`.
4. Відкрийте `http://127.0.0.1:3000/admin` і увійдіть зі своїми даними.

Локальні чернетки, зображення та обліковий запис зберігаються в `.admin-local/`, який виключено з Git. Це **не Supabase і не production-персистентність**. При `TOUR_DATA_SOURCE=local` каталог читає те саме сховище, але показує лише опубліковані, видимі, неархівні записи. Локальний каталог потребує `NODE_ENV=development`, `ADMIN_MODE=local` і localhost. Під `pnpm build` / `pnpm start` локальний доступ вимкнений; для production-збірки з переглядом використайте `TOUR_DATA_SOURCE=demo`.

Після збереження відкрийте «Предпросмотр сохранённой записи» в редакторі: `/admin/tours/<UUID>/preview`, або додайте `?locale=en`. Перегляд доступний лише авторизованому локальному адміністратору й показує збережені дані. Чернетки не доступні через `/ru/tours/<slug>`; їх фотографії доступні лише через захищений адміністративний endpoint. Після публікації відкрийте `/ru/tours` чи `/en/tours` та сторінку країни/напрямку. Локальні зображення не проходять через спільний кеш Next Image; після приховування/архівування доступ до їх публічного URL припиняється, якщо їх не використовує інший опублікований тур.

Вбудований демотур збережено окремо: `/ru/demo/tours/demo-ha-long` та `/en/demo/tours/demo-ha-long`. Він не додається до робочого локального каталогу. У режимі `demo` стара адреса `/ru/tours/demo-ha-long` також працює. Неперевірені/прострочені ціни та неперевірені дати у звичайному локальному каталозі приховані; приватний перегляд показує введені ціни. Бронювання завжди вимкнене.

Локальний довідник містить наявні демонстраційні напрямки, без вигаданих операторів, міст і курортів. Поля міста/курорту та операторів заповнюються із реального довідника Supabase після інтеграції. Для перевірки публікації локального зразка позначте «Демонстрационные данные» і заповніть обидва описи, фото та тривалість. Такий зразок можна побачити в локальному каталозі після публікації; до реального Supabase-каталогу він не допускається.

Збереження використовує файлове блокування та атомарну заміну одного JSON-файлу: невдалий пакет не змінює попередні дані. Після аварійного завершення процесу може залишитися порожня директорія `write.lock`; прибирайте її вручну лише після зупинки всіх локальних серверів і перевірки резервної копії. Для QA доступний `ADMIN_LOCAL_DIRECTORY`, обмежений підкаталогами `.admin-local/`; звичайному користувачу його задавати не потрібно.

## Налаштування реального збереження

Спочатку використайте **окремий тестовий Supabase-проєкт**, не існуючі сервіси VIETVOYAGE.

1. Застосуйте міграції у порядку:
   - `supabase/migrations/202610100001_tour_inventory.sql` (лише якщо основної схеми ще немає);
   - `supabase/migrations/202610100002_admin.sql`;
   - `supabase/storage-admin.sql` для Storage bucket та політик.

   Файли призначені для одноразового запуску в новому проєкті. Усі три виконуються транзакційно. Storage-скрипт зупиняється без змін, якщо вже існує bucket `tour-images` або будь-які політики на `storage.objects`: їх потрібно окремо перевірити, а не видаляти для обходу захисту. Приватний bucket автоматично не стає публічним.
2. Створіть/запросіть користувача через Supabase Authentication. Знайдіть його UUID та надайте роль через довірений SQL Editor:

```sql
-- Замініть UUID на id створеного користувача. Це не публічний API.
insert into public.admin_members(user_id, role)
values ('REPLACE_WITH_AUTH_USER_UUID', 'admin')
on conflict(user_id) do update set role = excluded.role;
```

3. Налаштуйте серверне середовище:

```dotenv
ADMIN_MODE=supabase
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
NEXT_PUBLIC_SITE_URL=https://YOUR_VERIFIED_DOMAIN
TOUR_DATA_SOURCE=demo
```

4. Завантажте підтверджені `locations` (kind: `city`, `resort`, `destination`, optional `parent_id`) та `operators` через захищені інструменти Supabase. Вони стають доступними у селекторах. Для Турції `asian_territory_verified=true` означає фактично перевірену азиатську територію; не ставте прапорець автоматично. Підтверджений оператор має `verified_at`.
5. Перебудуйте і перезапустіть застосунок. Next Image додає домен Storage із конфігурації під час запуску/збірки. Для production потрібен HTTPS, оскільки cookie має `Secure`.
6. Перевірте в тестовому Supabase вхід, позбавлення ролі, публікацію, Storage upload/delete, CSV-відкат і читання анонімним клієнтом. Тільки після цього переключіть `TOUR_DATA_SOURCE=supabase`, щоб публічний каталог читав реальні перевірені записи.

**Service-role key не потрібен і не використовується.** Сервер працює з JWT поточного користувача та публічним anon key. JWT зберігається в HttpOnly / SameSite=Strict cookie, Secure у production, до однієї години. Після завершення сесії потрібен повторний вхід; refresh token у браузері не зберігається. Вихід очищає cookie цього браузера; негайне відкликання доступу здійснюється вилученням/зміною ролі `admin_members` або блокуванням користувача в Auth. Роль перевіряється заново на кожному запиті, а не довіряється `user_metadata`. `viewer` не отримує адміністративного доступу.

Не передавайте персональні дані у фотографіях: `tour-images` — публічний bucket для ліцензованих туристичних матеріалів, а не приватних документів. Завантаження приймає JPEG/PNG/WebP до 8 МБ, перевіряє фактичний формат, декодує й перекодовує у WebP без метаданих, обмежує розмір до 2400 px та 40 млн вхідних пікселів. Назви файлів випадкові й незмінні. Видалення дозволене лише для завантажених матеріалів, які більше не використовуються турами. Фото публічної основи сайту не видаляються.

Перед видаленням сервер викликає захищену `admin_image_is_unused`; Storage DELETE-політика повторює перевірку. Враховуються фотографії чернеток, архіву й прихованих турів, public/signed/authenticated/render URL, параметри та percent-encoding. Неоднозначний Storage URL блокує видалення, доки його не виправлено. Публічні URL доступні також для фотографій чернеток. Внутрішній `operators.external_reference` недоступний браузерним ролям.

## Робочий процес

- Додайте екскурсію: адреса латиницею, країна, напрямок, категорія, назви RU/EN. Інші розділи можна поступово заповнювати у чернетці.
- Редагуйте абзаци/переліки, структуровану програму, FAQ, зустріч/забір, транспорт, умови, SEO, ціни та розклад. Перша фотографія галереї — обкладинка; порядок змінюється стрілками.
- Ціни: одна актуальна конфігурація на валюту з дорослою/дитячою сумою, віком дитини та періодом дії. Редактор замінює конфігурацію цін туру, а не веде історичний реєстр тарифів. Перед редагуванням старого інвентарю з багатьма історичними тарифами збережіть їх окремо. Публічно показуються тільки перевірені ціни з чинним періодом.
- Розклад сам по собі не створює доступності. Календарні записи мають конкретну дату/час, місткість, статус і дату перевірки. Кількість зайнятих місць не редагується; дати із зайнятими місцями захищені від видалення.
- Публікація реального туру потребує RU/EN назв і описів, фото, тривалості, перевіреного оператора й дати перевірки туру. Видимість та «рекомендуемая» налаштовуються окремо. Чернетки, архів, приховані, неперевірені й демонстраційні записи не видаються анонімному каталогу.
- Копіювання створює нову чернетку, скидає featured та підтвердження цін/дат, закриває календар і не переносить бронювання. Архівування знімає публікацію; зняти прапорець архіву можна в редакторі.
- Збереження перевіряє версію. Якщо інший адміністратор змінив екскурсію, застарілий запис відхиляється. У Supabase зберігається журнал `admin_audit_events` без паролів або токенів.

## CSV

`/admin/import` → «Скачать CSV-шаблон» → вибір файлу → «Проверить импорт» → перевірка всіх рядків → «Сохранить … черновиков».

UTF-8 із/без BOM, кома, стандартне екранування CSV-лапок, до 2 МБ / 1000 рядків за пакет. Обов’язкові колонки: `slug,country,location,category,title_ru,title_en`. Інші колонки можна прибрати. `country`, `location`, `city`, `resort`, `category` — slug зі справочників; `operator_id` — існуючий UUID. Суми десяткові з крапкою; boolean — `true` / `false`. Рядки з невідомими країнами, довідниками, некоректними датами, негативними цінами або повторними slug відхиляються. Наявні тури ніколи не перезаписуються CSV-імпортом.

Опис, highlights, inclusions/exclusions — абзаци або пункти через `|` чи нові рядки всередині CSV-лапок. Галерея/кілька валют/програма/FAQ/місця зустрічі та забору/розклад/дати підтримують JSON-колонки, які відповідають типам `AdminTour`:

- `gallery_json`: масив `{url,alt:{ru,en}}`, альтернатива `image_url` і підписам;
- `prices_json`: масив `{currency,adult,child,childMinAge,childMaxAge,validFrom,validUntil,verifiedAt}`, альтернатива окремим полям ціни;
- `itinerary_json`: `{title:{ru,en},description:{ru,en},durationMinutes}`;
- `schedule_json`: `{weekdays:[0..6],time,validFrom,validUntil}`;
- `slots_json`: `{date,time,capacity,reserved:0,status,verifiedAt}`;
- `faq_json`: `{question:{ru,en},answer:{ru,en}}`;
- `pickup_locations_json`: `{name:{ru,en},address:{ru,en},location,instructions:{ru,en}|null}`;
- `meeting_points_json`: `{name:{ru,en},address:{ru,en},lat,lng}`.

Вкладені лапки екрануються стандартним CSV-подвоєнням. Порожні JSON-колонки означають порожні масиви; пусті значення цін не означають безкоштовний вхід. Усі тури імпортуються як чернетки, без автоматичної перевірки туру. Навіть після успішного попереднього перегляду сервер знову перевіряє файл і дублікати. Одне SQL RPC зберігає весь пакет в одній транзакції; будь-яка помилка відкочує також дочірні записи та аудит. Локальний режим виконує аналогічну атомарну заміну файлу.

## Перевірки й межі інтеграції

`pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`.

Тести перевіряють підпис/строк сесій, пароль, ролі, CSRF, заборону локального production-режиму, модель туру, CSV, файловий відкат, ліміти запитів та зображення. PGlite запускає обидві міграції у тимчасовій PostgreSQL і перевіряє реальні RLS/RPC для anon, користувача без ролі й адміністратора, відкат, конфлікти версій, приховані записи, незаповнені старі чернетки та захист зайнятих місць. Auth UID симулюється в тестовій базі; реальний Supabase Auth/Storage ще потрібно перевірити з вашими обліковими даними.

Storage SQL також виконується локально в PGlite з мінімальною моделлю `storage.buckets` / `storage.objects` і RLS. Регресійні тести перевіряють усі три файли разом, широкі успадковані дозволи, відсутність TRUNCATE/зайвого EXECUTE, відкликання адміністративної ролі, заборону зміни зображень, захист використаних фотографій і повний відкат при наявному приватному bucket або невідомих політиках. Це перевірка PostgreSQL-політик, а не реального HTTP API Supabase Storage.

Список і статистика використовують компактний `admin_overview` без описів, галерей та календарів усіх турів; редактор завантажує лише вибрану екскурсію. Пошук/фільтри та сторінки по 25 записів працюють зі зведеними даними. Окремий SQL-тест перевіряє огляд із 360 тимчасовими записами.

Вигляд панелі й базові дії перевіряються у браузері на desktop/mobile з ізольованими тестовими даними. Бронювання, платежі, надсилання підтверджень та production-міграції не виконуються цією фазою.

## Зовнішні продукти — CSV / JSON

Локальна сторінка `/admin/import` містить новий імпорт із provider/ID, пакетами, попереднім переглядом і журналом. Старий CSV-імпорт власних екскурсій залишився в окремому розкривному розділі. Формат, ізоляція тестових даних, правила повторного імпорту та підготовка Klook описані в `EXTERNAL_IMPORT.md`. Нові зовнішні продукти зберігаються тільки локально; Supabase-імпорт цього формату ще не ввімкнений.
