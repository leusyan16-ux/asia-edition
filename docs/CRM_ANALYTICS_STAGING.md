## CRM та аналітика

Застосувати повний файл supabase/migrations/202611110010_commerce_crm_analytics.sql
у SQL Editor нового staging. Він додає таблиці CRM-етапів, нотаток і агрегованої
аналітики, RLS та функції з перевіркою чинної ролі та MFA.
Таблиці каталогу й вихідні редакційні картки не змінюються.
До застосування 010 нові адміністративні розділи показують повідомлення
про відсутню міграцію. Існуючі заявки та каталог працюють окремо.

Маршрути:

- /admin/orders — заявки, побажання, контакти, внутрішні етапи, нотатки й історія.
- /admin/customers — зареєстровані клієнти, email/телефон/ім'я, дати, пошук, 50 рядків на сторінку.
- /admin/analytics — Dashboard, події, приблизна географія, пристрої та джерела.
- /admin/staff — наявне керування ролями.

Для Owner використайте наявний supabase/commerce-owner-bootstrap.sql.
Authentication → Users → власний підтверджений email → Copy User UID.
Замініть нульовий UID у копії SQL і виконайте в цьому staging.
Потім додайте та підтвердьте TOTP у /ru/account/profile.
Не призначайте права довільному першому користувачу.

## Автоматичні повтори Telegram

Нова заявка запускає доставку після серверної відповіді незалежно від кнопки
Telegram. Черга 009 переживає збій і зберігає номер наступної частини.
Після втрати відповіді Telegram повтор інколи може дублювати останню частину
з тим самим номером заявки. Exactly-once доставка зовнішнім API не гарантується.

Для повторів без відвідувачів використайте наявний Supabase Cron.
В Integrations увімкніть Cron і pg_net.
У Vault збережіть наявний COMMERCE_TELEGRAM_CRON_SECRET під ім'ям
asia_edition_telegram_cron, а чинний Vercel Automation Bypass Secret —
під ім'ям asia_edition_vercel_bypass.
Виконайте supabase/commerce-telegram-schedule.sql тільки в staging.
Він створить або оновить одну задачу щохвилини з посиланнями на Vault.
Не вставляйте секрети у git, SQL-файли, URL або журнали.
Перевірте Cron → History та HTTP-відповіді. Створення розкладу локально не виконано.

## Методика статистики

Відвідувач сам обирає згоду, може відмовити й змінити її внизу сторінки.
До згоди події не надсилаються. У приватних формах не відстежуються значення.
IP використовується лише в пам'яті для денного HMAC разом із User-Agent.
Сіль змінюється щодня. Повний IP, координати та облікові токени не зберігаються.
Статистика зберігається до 35 днів. Видалення старих агрегатів виконується
при надходженні нових подій.

Один відвідувач означає приблизну мережеву пару адреси й браузера за день.
За 7/30 днів показуються відвідувач-дні, не унікальні люди.
Послідовність подій і різниця початків/завершень оформлення не доводять
реальні відмови окремих користувачів. Конверсія — частка відвідувач-днів
з подією успішного надсилання серед тих, хто погодив статистику.
Географія береться з серверних Vercel-заголовків і є приблизною.
Без даних показується Unknown. Минулі відвідування не відновлюються.

## Обмеження

Публічний каталог використовує затверджений статичний знімок, а commerce_products —
лише серверний mirror для заявок. Нова CRM не переносить каталог у Supabase.
Старий редактор каталогу залишається вимкненим у безпечному Preview;
для його записів потрібен окремо погоджений адаптер.
Доставка реального листа й вхід власника потребують перевірки з його поштою.
